# 项目介绍与答辩提纲

## 简历表述参考

**页间：基于 LangGraph 的资料学习助手**

技术栈：Python、LangGraph、OpenAI Python SDK、Pydantic、SQLite、原生 JavaScript、Windows COM。

- 构建讲义到笔记、练习题与复习卡片的本地工作流，支持 PDF/PPTX/TXT/Markdown 导入和 Word/Markdown/Anki/JSON 导出。
- 使用 LangGraph 动态任务分发、共享状态归并及并行汇聚，实现分段提取、出题与制卡并行、证据审核；以证据编号交接减少模型自由生成引用带来的错误。
- 实现严格结构校验、有界修正、审核截断拆批、1–8 路并发与请求预算；65 项自动测试通过，并完成 13 页课件的真实模型流程验证。

请按自己实际掌握的部分调整。AI 辅助开发可以如实说明；不要把“运行过”写成“完全独立从零实现”，也不要写未测量的准确率提升、提速比例、用户规模或商业落地。

## 一分钟介绍

我做的是一个本地资料学习助手。用户上传讲义或课件，系统把它拆成带来源的证据，再让模型分别提炼知识、出题和制作卡片，最后审核后导出。

我关注的重点是模型工作流如何可靠落地：并行任务怎样合并，下一步应该收到哪些上下文，格式和引用错误怎样恢复，以及如何控制并发和请求消耗。项目中用 LangGraph 定义执行顺序和共享状态，Pydantic 校验结果，程序根据证据编号回填原文，审核节点再判断支持关系。

它是个人作品集初版。目前重点支持 Windows；没有宣称编排必然更快，也没有把引用匹配当作事实正确的保证。

## 常见答辩问题

### 1. 这是多 Agent 还是模型流水线？

更准确地说是多角色模型工作流。各节点负责不同角色，图和控制逻辑由程序定义。它展示了多 Agent 系统常见的分发、交接、汇聚和审核模式，但不是自主决定工具和步骤的通用 Agent 群。

### 2. 为什么不用单次大提示词？

分开后每个节点的输入、输出和失败点更清楚，独立任务可以并行，审核也能单独处理。代价是更多模型请求、更高用量和额外延迟。短任务未必值得编排，需要按效果和成本选择。

### 3. 共享状态会一直变大吗？

图中会保存本次任务的阶段性结果，但给模型的上下文是程序选择的。本项目生成节点每批最多拿 8 个知识点及相关证据，审核每批最多 5 条，不会把全部历史不断追加到每个节点。

### 4. 怎样防止编造引用？

模型只选择本批已有证据编号，程序回填摘录并逐字匹配原文。这样能阻止伪造编号或改写摘录；还要用语义审核判断引用是否支持结论。摘录存在不代表结论必然正确，视觉描述也可能识别错误。

### 5. 审核节点真的起作用了吗？

真实样例中 108 条候选被审核删除 6 条证据不足项，保留 102 条。这个结果证明删除路径在一次实际调用中工作，不代表正确率提高了某个百分比。

### 6. 如何处理截断和错误？

格式错误最多修正一次；明确长度截断时，审核拆成更小批次。单条仍失败、网络/HTTP 失败或预算耗尽时停止。结束原因按类型记录，不把所有异常都说成 token 不够。

### 7. 并发是越高越好吗？

不是。并发上限取决于服务的并发、RPM、TPM 和资源池限制。项目让用户选 1–8 路，任务保留配置快照；模型调用和连接测试共享实例内的 limiter。429 还可能与余额有关，单纯降低并发不一定有效。

### 8. Key 如何保存？

默认仅在内存中，可选择 Windows 当前用户 DPAPI 加密保存；数据库、浏览器持久化和导出都不含 Key。它依赖原用户环境，不是跨电脑的通用保险箱。

### 9. 为什么 PPTX 需要 PowerPoint 和视觉模型？

本地解析能读文字，但箭头、图片和复杂布局需要整页图。当前使用 PowerPoint 渲染，再由视觉模型识别，避免要求用户手动转 PDF。这个选择缩小了兼容范围，暂不支持 WPS 和跨平台渲染。

### 10. 下一步怎么改进？

先建立固定的去敏评估集，统计引用支持、覆盖率和失败类型，再比较单模型与编排的实际成本/延迟。之后再考虑 checkpoint 续跑、更多渲染后端或检索；不把这些尚未实现的功能写进已完成经历。
